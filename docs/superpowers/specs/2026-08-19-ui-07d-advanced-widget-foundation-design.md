# UI-07D Advanced Widget Foundation — Design

## Status

Approved design for the fourth UI-07 slice on top of `ui-07-responsive-a11y-hardening`.

UI-07D is a presentation subsystem. It improves form and relationship interaction without changing business types, authorization, storage policy, mutation semantics, or adapter ownership.

## Goals

1. Introduce a typed public `presentation=` API for fields and relationships.
2. Keep domain/data semantics in `rakit-core` and browser interaction/rendering in `rakit-web`.
3. Ship a curated first wave of advanced widgets with strong keyboard/accessibility and progressive-enhancement behavior.
4. Reuse existing query, relationship, storage, permission, CSRF, validation, and mutation pipelines rather than creating parallel engines.
5. Preserve the existing `widget: str` hint as compatibility input while making typed presentations the preferred API.
6. Keep no-JavaScript critical flows usable, including large relationship candidate sets.

## Non-goals

UI-07D does not add rich text, code editors, repeaters, key/value or JSON editors, tag creation, generic composite-field infrastructure, multi-file storage semantics, image editing, ORM-specific widget behavior, authorization/validation bypasses, Playwright/axe infrastructure, or broad UI-08 polish.

## Architectural boundary

The public API uses immutable typed presentation objects. Direct declarations carry the presentation inline:

```python
field = FieldDefinition(
    field_id="price",
    python_type=Decimal,
    presentation=Currency(currency="IDR", locale="id-ID"),
)

relationship = RelationshipDefinition(
    relationship_id="customer",
    target_resource_id="customers",
    label="Customer",
    kind=RelationshipKind.MANY_TO_ONE,
    cardinality=RelationshipCardinality.TO_ONE,
    presentation=Autocomplete(
        search_fields=("name", "email"),
        display_fields=("name", "email"),
        placeholder="Search customer...",
    ),
)
```

`rakit-core` does **not** import presentation classes. `FieldDefinition.presentation` and `RelationshipDefinition.presentation` are opaque optional objects carried through compilation only. Core parsing, mutation, authorization, query, and storage code never branch on presentation types.

Fields generated by adapters cannot be conveniently declared inline by application code, so `ResourceWebPresentation.fields` and `.relationships` provide web-only overrides. Resolution order is:

```text
ResourceWebPresentation override
    -> inline opaque presentation on direct definition
    -> legacy FieldDefinition.widget compatibility
    -> safe type/cardinality default
```

This preserves the preferred `presentation=...` ergonomics for direct definitions while keeping generated-model customization practical and preserving dependency direction.

```text
public Rakit API
FieldDefinition / RelationshipDefinition
        │
        ├── semantic definition ──> rakit-core
        │      └── opaque presentation reference only
        │
        └── optional ResourceWebPresentation override
                  │
                  └──> rakit-web PresentationRegistry
                            ├── semantic HTML
                            ├── progressive-enhancement hooks
                            └── shared JS/CSS behavior
```

Presentation objects may format, constrain interaction, and choose browser affordances. They must not change the canonical business type or become an alternate mutation/query/storage engine.

## Presentation contract

A presentation is an immutable value object with a stable internal key. Built-ins are typed classes rather than string option dictionaries.

First-wave families:

- Choice/relationship: `Select`, `SearchableSelect`, `Autocomplete`, `MultiAutocomplete`.
- Date/time: `DatePicker`, `TimePicker`, `DateTimePicker`, `DateRangePicker` (typed range only in v1).
- Numeric: `NumberInput`, `Currency`, `Percentage`.
- Boolean/small choice: `Checkbox`, `Switch`, `SegmentedControl`.
- File: `FileUpload`, `ImageUpload`.

All classes validate their configuration at construction time.

## Inference and compatibility

Conservative inference:

```text
str       -> basic text
bool      -> Checkbox
int       -> NumberInput
float     -> NumberInput
Decimal   -> NumberInput
date      -> DatePicker
datetime  -> DateTimePicker
enum      -> Select
file      -> basic file / FileUpload-safe fallback
relation  -> current safe relationship UI
```

Rakit must not infer currency, percentage, switch semantics, or remote autocomplete solely from Python type or runtime row counts.

`FieldDefinition.widget` remains accepted. It is compatibility input, not the preferred advanced API.

## PresentationRegistry

`rakit-web` owns one centralized registry mapping presentation types to renderer contracts.

Conceptually:

```python
registry.register(Autocomplete, renderer=autocomplete_renderer)
```

A renderer may consume field/relationship metadata, canonical current value, validation issues, resolved candidate endpoint metadata, and presentation configuration. It may produce semantic view-model data and deterministic `data-rakit-*` enhancement hooks.

A renderer must not access databases directly, authorize requests, bypass `FormSchema`, execute mutations, control storage policy, or render unescaped arbitrary user HTML.

Minimal custom server-rendered presentation registration is supported in v1; full plugin packaging is deferred.

## Choice and relationship behavior

### Select

Small bounded choices. Native `<select>` remains implementation/fallback.

### SearchableSelect

Small-to-medium choices safe to render in full. Browser search is local; no remote request is required.

### Autocomplete

One canonical identity from a potentially large candidate set:

```python
Autocomplete(
    search_fields=("name", "email"),
    display_fields=("name", "email"),
    placeholder="Search customer...",
    min_query_length=2,
    page_size=20,
)
```

Display labels are never source-of-truth form values. The browser submits canonical encoded identity.

Candidate transport is adapter-neutral and bounded:

```text
items:
  - identity
  - label
  - optional description
continuation/page metadata
has_more
```

Lookup reuses resource visibility, exact relationship permissions, searchable-field policy, query limits, sorting, and pagination. `page_size` is server-bounded. Current page-based datasource support may back the first implementation; the contract must not prevent cursor continuation later.

### MultiAutocomplete

Uses the same candidate contract with multiple canonical identities. Selected items render as removable chips; selected identities are deduplicated.

### Interaction and ARIA

Autocomplete keeps focus on the textbox and uses the combobox/listbox pattern: `role="combobox"`, `aria-expanded`, `aria-controls`, `aria-activedescendant`, listbox popup, option roles, and restrained live-region announcements.

Required keyboard behavior:

```text
ArrowUp/ArrowDown -> move active option
Enter -> select
Escape -> close
nullable clear -> clear current single selection
multi selection -> keep input focused
Backspace on empty multi input -> remove last chip
```

Remote requests are debounced and race-safe: stale responses cannot overwrite newer results.

## No-JavaScript candidate fallback

Remote autocomplete must not degrade to unbounded `<select>` markup. The fallback is a server-rendered searchable/bounded picker under the existing relationship route, using the same authorization and query restrictions and returning canonical identity values to the normal form flow.

## Date and time presentations

- `DatePicker`: canonical `date`; fallback `<input type="date">`.
- `TimePicker`: canonical supported time type; fallback `<input type="time">`.
- `DateTimePicker`: canonical `datetime`; fallback `<input type="datetime-local">`; timezone conversion is explicit/application-policy-driven, never guessed silently.
- `DateRangePicker`: v1 supports one typed range value only; generic `start_date + end_date` composition is deferred.

## Numeric presentations

`NumberInput`, `Currency`, and `Percentage` never create new business datatypes. Canonical types remain `int`, `float`, or preferably `Decimal` for money. Locale formatting is presentation/parser assistance only. Percentage scale semantics must be explicit.

## Boolean and small-choice presentations

- `Checkbox`: default boolean presentation.
- `Switch`: boolean presentation for mutable enabled/disabled state; underlying semantics remain checkbox-like.
- `SegmentedControl`: small mutually-exclusive choices, normally 2–4; no-JS fallback is radio controls.

## File and image presentations

Existing `FileField` remains authoritative for storage id, prefix, size, MIME/extension restrictions, filename policy, and delete behavior.

`FileUpload` enhances one canonical file value with drag/drop, selected file summary, replace/clear pending selection, existing-file presentation, and progress where normal transport exposes it. Fallback remains `<input type="file">`.

`ImageUpload` adds safe local thumbnail preview/dimensions. UI-07D does not add crop, rotate, compression/transformation policy, or multiple-file semantics.

## Custom presentation boundary

Developers may define immutable custom presentation objects and register web renderers through the presentation registry. Standard pipelines still own validation, authorization, CSRF, candidate visibility, storage policy, and mutations.

## Asset policy

Advanced behavior is centralized in shared Rakit CSS/JS modules. No per-template inline widget scripts. The runtime may track required widget families so future asset splitting remains possible; UI-07D does not require micro-bundling each widget.

## Error states

Autocomplete distinguishes query-too-short, zero results, request failure, and selected identity no longer available. Server submission remains authoritative for stale/unauthorized identities.

## Security and policy invariants

UI-07D preserves permission/capability fail-closed behavior, CSRF/submission-token handling, relationship authorization, candidate visibility restrictions, file/storage policy, canonical identity transport, progressive enhancement, and the rule that the browser is never an authorization boundary.

## Implementation discipline

Project workflow:

```text
source/behavior implementation
-> structural/non-test review
-> regression tests
-> focused verification
-> full repo CI
```

Tests prefer semantic/behavior contracts over brittle full-HTML snapshots.

## Acceptance criteria

UI-07D is complete when:

1. direct field/relationship definitions accept inline typed presentations as opaque metadata without a core-to-web dependency;
2. adapter-generated fields/relationships can be overridden through `ResourceWebPresentation`;
3. resolution is deterministic: sidecar override -> inline -> legacy widget -> safe default;
4. registry rendering is centralized and minimal custom registration works safely;
5. SearchableSelect, Autocomplete, and MultiAutocomplete provide keyboard-accessible interaction;
6. remote candidates use canonical identity, permissions, query restrictions, bounded pagination, and race-safe browser behavior;
7. large relationship selections have a usable no-JS picker fallback;
8. date/time, numeric, boolean, file, and image presentations preserve canonical data/storage contracts;
9. shared widget assets are semantic, responsive, theme-compatible, and reduced-motion compatible;
10. deterministic showcase states cover representative first-wave widgets;
11. focused and full repository verification pass before merge into the UI-07 epic;
12. combined UI-07 browser acceptance is repeated after UI-07D integration before the epic is proposed to `main`.

## Deferred wave

Deferred after UI-07D: `TagInput`, `Repeater`, `KeyValueEditor`, `JsonEditor`, rich text, code editor, `MultiFileUpload`, image editing, generic cross-field composite engine, and advanced presentation plugin packaging.
